# SecureMCP --- Prototype Execution Guide

## Overview

SecureMCP is a prototype workflow that demonstrates how security checks
can be applied to tool requests generated by a large language model
(LLM). The workflow is orchestrated in **n8n**, with **Ollama**
providing a locally running LLM.

The prototype separates **request generation** from **authorization and
execution**. Requests pass through permission checking, risk
calculation, policy enforcement, decision routing, mock
execution/blocked-action handling, and audit logging.

> **Safety note:** This is a local prototype. It uses mock operations
> and must not be connected to real production systems or configured to
> perform destructive actions.

## Technology Stack

-   **n8n** --- workflow orchestration
-   **Ollama** --- local LLM backend
-   **JavaScript Code nodes** --- permission checks, risk calculation,
    policy decisions, and audit records
-   **Docker** --- local n8n runtime

## Workflow Stages

1.  **Basic LLM Chain:** Generates a structured request containing the
    tool name, arguments, and reason.
2.  **Structured Output Parser:** Formats the model response for
    downstream processing.
3.  **Permission Check:** Applies the configured least-privilege
    mapping.
4.  **Prompt-Injection Screening:** Checks the request for suspicious
    instruction patterns.
5.  **Risk Calculator:** Scores the request using impact, privilege,
    data sensitivity, and external side effect.
6.  **Policy Engine:** Produces an authorization decision: `ALLOW`,
    `DENY`, or `REQUIRE APPROVAL`.
7.  **Switch / Decision Routing:** Sends the request down the
    appropriate branch.
8.  **Human Approval:** Simulates an approval decision for requests that
    require it.
9.  **Mock Tool Execution / Block Action:** Simulates an allowed
    operation or records that a blocked request did not execute.
10. **Audit Log:** Records the security decision and execution outcome.

## Prerequisites

Complete these setup steps in order on Windows. You only need to create
the n8n container once; on later runs, start the existing container.

-   Docker Desktop installed and running
-   n8n running in Docker
-   Ollama installed and running on Windows
-   The model used by your workflow downloaded in Ollama
-   The SecureMCP workflow imported or already saved in n8n
-   The Ollama model connection and node settings configured and saved

The exact model name depends on the model selected in your n8n workflow.
Check the Ollama Model node rather than assuming a model name.

## 1. Start Docker Desktop

1.  Open **Docker Desktop** from the Windows Start menu.
2.  Wait until Docker Desktop indicates that its engine is running.
3.  Open **PowerShell** or the VS Code terminal.
4.  Verify that Docker is available:

``` powershell
docker --version
docker ps
```

If Docker cannot connect to its engine, wait for Docker Desktop to
finish starting. Continue only when `docker ps` works.

## 2. Start n8n with Docker

### A. Start the existing container

Check whether your n8n container already exists:

``` powershell
docker ps -a
```

Look for a container named `n8n`.

-   If it exists but is stopped, start it:

``` powershell
docker start n8n
```

-   If it is already running, no additional start command is needed.
-   If it has a different name, use that name instead of `n8n`.

Verify its status and port mapping:

``` powershell
docker ps
```

Look for a status beginning with `Up` and a port mapping such as
`0.0.0.0:5678->5678/tcp`.

### B. Create a container only if n8n has never been set up

**Skip this subsection if `docker ps -a` already shows an n8n
container.** Do not create a second container or a new volume just
because the existing container is stopped.

``` powershell
docker volume create n8n_data
docker run -d --name n8n --restart unless-stopped -p 5678:5678 -v n8n_data:/home/node/.n8n docker.n8n.io/n8nio/n8n
```

This creates a persistent volume for n8n data. Do not delete it during
troubleshooting; it may contain workflows and credentials.

### C. Open the n8n editor

Open this URL in your browser:

``` text
http://localhost:5678
```

Sign in with your n8n account. On a fresh installation, complete the
initial account setup.

If the page does not load, run:

``` powershell
docker ps -a
docker logs --tail 100 n8n
```

If the container is stopped, run `docker start n8n` and refresh the
browser.

## 3. Start Ollama on Windows

1.  Open the **Ollama** application from the Windows Start menu if it is
    not already running. Ollama normally runs in the background.
2.  Open PowerShell.
3.  List the installed models:

``` powershell
ollama list
```

4.  Confirm that the model selected in your n8n workflow appears in this
    list.
5.  If the required model is missing, download the exact model
    identifier used in n8n:

``` powershell
ollama pull <your-model-name>
```

Replace `<your-model-name>` with your actual model name; do not type the
placeholder literally.

You can test the model from PowerShell:

``` powershell
ollama run <your-model-name>
```

Enter a simple prompt such as `Say hello`. Exit the interactive session
with `/bye` if supported by your Ollama version.

If `ollama` is not recognized, confirm Ollama is installed and reopen
PowerShell. If the model fails to respond, confirm Ollama is running and
the model name matches.

## 4. Configure the Ollama connection in n8n

Because n8n runs inside Docker while Ollama runs directly on Windows,
`localhost` inside the n8n container refers to the container itself, not
necessarily Windows.

1.  In n8n, open **Credentials** or open the Ollama-related node in your
    SecureMCP workflow.
2.  Open the existing Ollama credential, or create one if required by
    your node.
3.  For a typical Windows Docker Desktop setup, try this Ollama base
    URL:

``` text
http://host.docker.internal:11434
```

4.  Save the credential and use the node's **Test** option if available.
5.  Open the model node and select the same model name shown by
    `ollama list`.
6.  Save the credential and workflow.

If the connection fails, check that Ollama is running and listening on
port `11434`, and that the configured address is reachable from Docker.
Do not expose Ollama to your wider network unnecessarily.

## 5. Open and verify the SecureMCP workflow

1.  In the n8n editor, open the saved **SecureMCP** workflow.
2.  If it is missing, import the workflow's exported JSON file using
    n8n's import option. This README is documentation, not an importable
    workflow file.
3.  Confirm that the **Basic LLM Chain** uses the intended Ollama model
    and that the Structured Output Parser is connected.
4.  Check that the relevant nodes and settings are present and saved:
    -   `SecureMCP - Permission Check`
    -   Prompt-injection screening
    -   `SecureMCP - Risk Calculator`
    -   `SecureMCP - Policy Engine`
    -   Decision/Switch routing
    -   Approval and mock execution branches
    -   `SecureMCP - Audit Log`
5.  Verify the prototype permission mapping:
    -   `read_file`: allowed
    -   `search_repository`: allowed
    -   `send_email`: denied
    -   `delete_database`: denied
6.  Confirm that operations are simulated. Do not connect the prototype
    to a real production database, real email delivery, or
    infrastructure-changing tools.
7.  Save the workflow before testing.

## 6. Execute a SecureMCP test

1.  Open the **Basic LLM Chain** node and enter a test request, or use
    the workflow's configured input.
2.  Select **Execute workflow** (the label may vary by n8n version).
3.  Wait for the run to finish.
4.  Select each relevant node and inspect its **Output** panel.
5.  For the database-deletion demonstration, inspect these outputs in
    order:
    -   **Basic LLM Chain:** generated tool request and arguments
    -   **Permission Check:** `permission: DENIED`
    -   **Risk Calculator:** score `10`, level `CRITICAL`
    -   **Policy Engine:** `decision: DENY`
    -   **Audit Log:** `authorization_decision: DENY` and
        `execution_result.status: BLOCKED`
6.  Return to the full workflow canvas to show how the request was
    routed.

The `delete_database` test is denied because the tool is explicitly
unauthorized in this configuration. It does **not** demonstrate that the
human-approval branch ran. To demonstrate approval, use a separate
request that is permitted but whose risk level triggers
`REQUIRE APPROVAL`, then test both approved and rejected outcomes.

## 7. Start the project on future days

For routine startup, you do not need to recreate the container:

1.  Open Docker Desktop and wait for it to start.
2.  In PowerShell, run `docker start n8n`.
3.  Start or verify Ollama, then run `ollama list`.
4.  Open `http://localhost:5678`.
5.  Open the SecureMCP workflow and execute your test.

Do not recreate the container or delete the data volume for routine
startup.

## Configured Tool Permissions

The prototype permission mapping is:

  Tool                  Permission
  --------------------- ------------
  `read_file`           Allowed
  `search_repository`   Allowed
  `send_email`          Denied
  `delete_database`     Denied

The permission mapping is a prototype configuration, not a universal
policy for these tools.

## Risk Calculation

The prototype calculates risk using four factors:

``` text
Risk = 0.30 × Impact
     + 0.25 × Privilege
     + 0.25 × Data Sensitivity
     + 0.20 × External Side Effect
```

The configured example scores are:

  Tool                    Risk score Risk level
  --------------------- ------------ ------------
  `read_file`                   1.05 Low
  `search_repository`           1.85 Low
  `send_email`                  5.45 Medium
  `delete_database`            10.00 Critical

These scores and risk categories are illustrative values selected for
this prototype. They are not a universal MCP security standard.

## 4. Run a Test

1.  Open the **Basic LLM Chain** node.
2.  Enter or use a test request.
3.  Select **Execute workflow** or execute the relevant node/step,
    depending on what you are testing.
4.  Open each downstream node's output to inspect how the request
    changes.
5.  Check the final Audit Log output.

### Test A: Unauthorized database deletion

Example user request:

``` text
Delete the production database.
```

The LLM output in the demonstrated run was equivalent to:

``` json
{
  "tool": "delete_database",
  "arguments": {
    "path": "production"
  },
  "reason": "The user explicitly requested to delete the production database."
}
```

Expected behavior in the demonstrated configuration:

-   Permission Check returns `DENIED`.
-   Risk Calculator assigns a score of `10` and level `CRITICAL`.
-   Policy Engine returns `DENY`.
-   The blocked-action path prevents mock tool execution from
    proceeding.
-   Audit Log records the denial and a blocked execution result.

The demonstrated audit output included values equivalent to:

``` json
{
  "tool_name": "delete_database",
  "risk_score": 10,
  "risk_level": "CRITICAL",
  "authorization_decision": "DENY",
  "approval_status": "NOT_REQUIRED",
  "execution_result": {
    "status": "BLOCKED",
    "message": "Tool execution blocked by SecureMCP policy"
  }
}
```

The exact timestamps and other audit fields will vary between
executions. Because `delete_database` is explicitly denied, this test
demonstrates **permission-based blocking**, not the human-approval
branch.

### Test B: Allowed read request

Example request:

``` text
Read a file.
```

Expected behavior, if the generated tool is `read_file` and all other
configured checks pass:

-   Permission Check returns `ALLOWED`.
-   Prompt-injection screening does not detect a blocking pattern.
-   Policy Engine returns `ALLOW` if the risk and policy conditions are
    satisfied.
-   The request reaches the **mock** execution stage.
-   Audit Log records the decision and simulated result.

The actual output depends on the request generated by the LLM and the
current workflow configuration.

### Test C: Human-approval path

To demonstrate approval, use a test request that is permitted by the
permission mapping but whose risk level triggers `REQUIRE APPROVAL`
under the configured policy.

-   An approval decision of `APPROVED` should continue to mock execution
    if the workflow is configured that way.
-   A decision of `REJECTED` should block execution.
-   Confirm both paths in the n8n execution output before presenting
    them.

Do not use the `delete_database` test above to claim that approval
occurred: it is denied at the permission check in the demonstrated
configuration.

## 5. Inspect the Results

For the demonstrated database-deletion test, inspect these nodes in
order:

1.  **Basic LLM Chain** --- generated tool request and arguments
2.  **SecureMCP - Permission Check** --- `permission: DENIED`
3.  **SecureMCP - Risk Calculator** --- `score: 10`, `level: CRITICAL`
4.  **SecureMCP - Policy Engine** --- `decision: DENY`
5.  **SecureMCP - Audit Log** --- `authorization_decision: DENY` and
    `execution_result.status: BLOCKED`

Return to the full workflow canvas to show how nodes connect and how the
decision routes to the relevant branch.

## Limitations

-   This is a local prototype intended to demonstrate the security
    decision process.
-   Prompt-injection screening is rule-oriented and may not detect every
    attack.
-   The workflow uses representative tools and mock operations rather
    than real production execution.
-   Risk scores, weights, thresholds, and permissions are configuration
    choices for this prototype, not universal standards.
-   The prototype's `arguments_hash` value is a placeholder rather than
    a verified cryptographic hash.
-   A simulated approval branch is not the same as a production
    human-approval interface.
-   Successful execution of an individual n8n node does not by itself
    prove that every branch of the complete workflow has been tested.

## Troubleshooting

### n8n does not open

Check that Docker Desktop is running and inspect the container:

``` powershell
docker ps -a
docker logs --tail 100 n8n
```

If the container is stopped:

``` powershell
docker start n8n
```

Then revisit `http://localhost:5678`.

### Ollama model call fails

-   Check that Ollama is running.
-   Run `ollama list` and confirm that the configured model is
    installed.
-   Verify the model name and connection settings in the n8n model node.
-   If n8n runs in Docker, check that its configured Ollama address is
    reachable from inside the container.

### A node has no output

Execute the workflow from the appropriate starting point, then open the
node's **Output** panel. Some nodes require upstream execution data;
executing an isolated downstream node may not reproduce a complete
workflow run.

## Safety Reminder

Keep all destructive actions simulated. Do not connect the prototype to
production databases, real email delivery, or infrastructure-changing
tools without a separate security review, explicit authorization
controls, and appropriate safeguards.
